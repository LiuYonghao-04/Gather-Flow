# 工程默认与待决事项

这些是为当前实现补齐的默认行为，不等同于新增的用户已确认规则。

## M0 / M1 已应用

- 使用 npm workspaces；沿用官方 Vue 3 / TypeScript 模板，只保留微信和 H5 目标。
- Node 22.18、Express 5.1、better-sqlite3 12.4.1；本阶段不用 ORM，使用参数化 SQL 和版本化迁移，使原子消费与约束可直接审计。原需求允许 ORM 可选，未来可增适配层。
- 五个 demo 身份是演示用户资料，不代表真实身份；任何一个身份均可发起活动。只有种子活动的 A 固定为房主。
- 默认 API 绑定 127.0.0.1；开发环境默认 demo，生产模式禁止 demo。前端隐藏入口不构成授权，服务端独立拒绝。
- 会话 24 小时有效、只存哈希；切换身份不会删除旧会话，便于在多个开发工具窗口模拟不同用户。正式微信会话尚未接入。
- 邀请码采用 32 字节加密随机数（256 bit）、64 位十六进制表示；数据库存 SHA-256 哈希，原码仅生成时返回。当前无过期/撤销功能，已消费的免审权益永久不可恢复。
- 原生微信分享使用提前生成的邀请，发送时立即清空并预备下一张；取消分享可能留下未使用的邀请。重复复制保留同一卡，显式“生成新邀请”产生新码。转发保留原码。
- 已入组者点自己的新直邀不消耗资格，不重复创建成员。并发第二位申请者会收到 `APPROVAL_REQUIRED`，由其明确提交申请；服务端不静默代申请。
- 同一活动同一用户只能有一个待审申请。重复提交返回当前待审状态；拒绝后创建新的申请行，历史不覆盖。
- 有待审申请时，用户拿到新的未消费直邀可以直接加入，待审申请同时标记已解决；这不是伪造房主审批，`reviewer_id` 为空，直邀加入事件保留来源。
- 公开预览只返回活动 ID、名称、类型、状态和当前用户自己的加入/申请状态。活动简介、成员名单、审计均属于私有数据。
- 非成员即使猜中活动 ID，也统一得到无权限响应；不能通过详情接口枚举私有资料。
- 审计每次取 50 条，支持继续加载。活动、成员和待审列表当前按小型朋友群设计，尚未做大规模数据虚拟化或分页。
- 当前不提供活动删除、踢人、房主转让、退出成员或结束活动接口；避免尚未实现财务校验时提前开放结束入口。

## M2 / M3 已应用

- 一个提案是一项完整安排，创建时明确相关参与者（默认当时全体成员）。新加入成员不会静默进入旧方案的确认集合。参与范围需要改变时新提方案；退出仅针对该方案。
- 提案内容任意修订均增加版本，重收该提案全部参与者的表态，其他提案不受影响。同一版本中本人可以更正表态；历次更正保留在审计中。房主不能覆盖成员现存的异议，只能由本人更正或发布新方案后重新收集。
- 未关联任务的提案由原提案人编辑；关联任务后只有当前负责人编辑。原提案人可以把独立提案关联到自己已认领的任务，同时发布新版本、重新确认；已有任务关联不转移或解除。
- 修改任务正式内容增加任务版本、清除工作完成标记；其关联方案变为 STALE 并暂不进入总行程，直到负责人提交新版方案重新确认。接受一条建议只记录处理结果，不自动改写正式内容；负责人按需另行编辑。
- 待交接优先显示为 HANDOVER_PENDING，另保留 completed 布尔值。原负责人可以撤销尚未接受的申请；仅候选接手人能接受。一个负责人同时仅能有一份待处理交接；可交给已有共同负责人。
- 方案确定后、登记执行前仍可更正表态。BOOKED / DONE 锁定原方案及来源任务的实质内容，变更须建立补充任务/方案，避免悄然改写已预订事项。取消、退款和执行回滚不在本阶段。
- 总行程包含已确定方案，未定日期单独列出。时间按本地活动日期与 24 小时制处理；跨日安排拆段。冲突为同日共同参与者的时段重叠，以及交通结束晚于游玩开始的启发式提醒；不判断地点通达性、返程方向或自动挪动安排。
- 图片上限 5 MB / 2500 万像素，仅单张 JPEG、PNG、WebP；服务端解码、移除 EXIF，最长边压至 2400 像素并转为 JPEG。图片二进制保存在 SQLite BLOB，数据库是私有本地存储，**不代表静态加密或生产对象存储**；操作系统上有数据库访问权的人仍能读取图片。
- 仅当前任务负责人上传；关联方案时固定 proposalVersion。需要预订的方案必须有本版凭证才能登记 BOOKED 或 DONE。图片不自动改变预订状态，也不证明支付真实性。非预订事项可由负责人登记 DONE。
- 上传与可选记账在同页完成，使用相同凭证 ID。两次提交不是跨网络原子事务：图片先成功落库，记账失败保留图片和表单以便重试；已保存账单提供详情入口。凭证没有删除接口。
- 金额上限每笔 1,000,000 元，使用整数分。平摊尾差按成员 ID 的字典序依次加 1 分；客户端展示每人最终金额，服务端重新计算。自定义允许个别零分，但总额必须大于零、成员不重复、分摊合计精确相等。
- 任何活动成员可记账；仅原记账人能修订。所有修订（包括描述修正）均生成新版本、使旧版确认失效，采用较保守的默认行为。
- 异议从提出时保留到其作者明确撤销，即使账单后来修订、作者被移出新版分摊名单，也不自动撤销；该作者仍可撤销自己的旧异议。多个作者分别处理。已有确认不消灭异议。
- 单个分摊人且该人是付款者才是 PERSONAL_ONLY；付款人不同于唯一分摊人时仍是共享待确认账单。记账人不能自确认，付款者未被选为分摊人时也不能仅凭付款身份确认，但可以提出异议。
- 预计净额仅使用当前版本已确认、无异议的共同账单；确定性贪心配对不宣称全局最少笔数。待确认数、争议数、个人账单数分别显示。M3 不冻结账单，不生成最终清算或收款确认。
- 详情页每次显示重新拉取；输入页在同一身份返回时保留内存表单，身份变更会重载。费用列表分批渲染 20 条，API 仍返回该活动全部账单；规模按小型朋友活动设计。

## 后续阶段必须保留的原文工程默认

- 提案实质变化增加版本并重收受影响参与者确认；全员退出不能确定。退出不删除成员或历史消费责任。代理更正与方案锁定规则在 M2 写状态机时明确，不默默改变已确认规则。
- 时间偏好区分“倾向”和“只能”；正式任务内容、建议历史、交接责任分别记录。非财务任务未完成不阻止活动结束，但财务条件不能绕过。
- 需预订事项至少一份凭证才能标为 BOOKED；凭证不构成支付真实性判断。
- 金额用整数分，平摊尾差按固定成员顺序分配；自定义合计必须精确等于总金额。仅付款者消费标 PERSONAL_ONLY，不参与共同 AA。
- 清算使用确定性净额配对，金额守恒、不自转账、不宣称全局最少转账次数。
- 全部账单确认且无争议才能冻结快照。尚无到账确认可解除冻结重算；已有到账不得自动回滚。仅整笔确认，不做部分到账。
- 无共享账单时零金额结算可视为结清，但必须由房主明确结束；已结束数据只读。

## 刻意不做

真实支付/钱包/资金托管、OCR 与订单真伪判断、导航和票务直连、生产云部署、部分收款、取消与退款、房主转让、踢人。以上不在当前首版承诺范围内。
